|---|---|---|---|
| 스파이크 이전 (기본) | ~17ms | ~35ms | ~69ms |

| 지표 | 측정값 |
|---|---|
| CPU 사용률 | 0.6% |
| JVM 힙 사용량 | 122 MiB (평균) / 187 MiB (최대) |

| 최대 RPS (인기 메뉴) | **195 req/s** |
| 4xx 에러율 피크 | 15.7% |

> **4xx 에러율 15.7% 해석:**  
> Grafana의 4xx 에러는 스파이크 피크 구간(22:55 부근)에서 발생했다.  
> k6의 커스텀 error_rate는 0.00%로 측정되어, 해당 4xx는 동시에 진행된 수동 API 탐색  
> (포인트 충전, 주문 생성 등 Rate Limiting 적용 엔드포인트)에서 발생한 것으로 추정된다.  
> k6가 테스트한 GET /api/menus/popular 에서는 에러가 한 건도 없었다.

### 분석

200 VU 급증 시 P99가 308ms(Grafana 기준)까지 상승했으나 k6 측정 기준 9.86ms로 목표(3,000ms)를 크게 하회한다.
이 차이는 Grafana가 Prometheus scrape 주기(5s) 기준으로 집계하는 반면 k6는 개별 요청 단위로 측정하는 방식의 차이에서 기인한다.
스파이크 해소 후 응답시간이 즉각 정상 수준(3~5ms)으로 회복된 점은 시스템 복원력이 양호함을 나타낸다.
GC 일시정지가 스파이크 피크에서 778μs로 증가했으나 사용자 체감에 영향을 줄 수준은 아니다.

## 7. 결론

읽기 경로(메뉴 목록, 인기 메뉴)는 250 VU, 124.5 RPS 부하에서도 P99 5ms 이내, 에러율 0.00%를 달성하며 매우 안정적인 성능을 보였다. JVM 힙 사용률 2.2%, CPU 0.6%로 리소스 여유도가 충분하여 현재 스펙 대비 훨씬 높은 트래픽을 수용할 수 있다.

동시성 테스트에서는 비관적 락이 의도대로 동작하여 포인트 잔액과 재고 수량이 모든 경우에서 정합성을 유지했다.

향후 AWS EC2 2대 + RDS + ElastiCache 환경에서 쓰기 경로(주문 생성, 포인트 충전)를 포함한 부하 테스트를 진행하면 분산 락, 비관적 락, Kafka 이벤트 처리 지연 등 실제 운영 환경의 성능 한계를 더 정확하게 측정할 수 있다.
